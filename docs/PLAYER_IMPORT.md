# Importing the Messenger roster

The local importer reads the JSON export from `tools/messenger-members/out/members.json`. It never connects to Messenger, sends messages, or creates accounts. Team assignment and unknown playing details remain unset. Exactly two teams exist; **Unassigned** means a player has no primary team yet.

## Separate real-club Docker setup

The demo at port 8080 keeps its own database. `compose.real.yaml` uses project `lex-pickup-real`, its own PostgreSQL volume, an independent JWT secret and session cookie, and localhost port **8081**. Demo mode and open registration are disabled. Requires Docker Compose 2.24.4+ for `!override`.

For a new installation, copy `.env.real.example` to `.env.real`, restrict it with `chmod 600 .env.real`, and fill `REAL_JWT_SECRET` and `POSTGRES_PASSWORD` with separate values generated by `openssl rand -hex 32`. Do not replace an existing database password or secret when rerunning these steps.

From the repository root, this shell helper keeps every command on the real project:

```sh
realclub() {
  docker compose --env-file .env.real -f compose.yaml -f compose.real.yaml "$@"
}
realclub up -d --build
```

Startup migrates the database and initializes only the two teams and an active season. This configuration is for local use; follow [deployment instructions](DEPLOYMENT.md) for public HTTPS hosting. Keep `.env.real`, exports, review manifests and database backups private. The export directory is ignored by Git and is never part of either image build context.

## Preview and review

Preview is the default and never writes to the database. Stream the source into the running backend; the report stays on your computer:

```sh
# Use a new report filename; do not overwrite a previously reviewed manifest.
(umask 077; set -C; realclub exec -T backend python -m app.import_players \
  --file - --dry-run < tools/messenger-members/out/members.json \
  > tools/messenger-members/out/import-review.json)
```

Check the command exit code before reviewing the file. Counts go to stderr, JSON to stdout. A CLI `--report PATH` option instead creates a private file and refuses to overwrite an existing file. Source files must be UTF-8 JSON arrays with `name`, `profileUrl`, `photoUrl` and `role` strings; malformed input stops the entire import.

The manifest contains the exact file SHA-256 fingerprint, original names, proposed names, generated UUIDs and these decisions:

| Action | Meaning |
| --- | --- |
| `create` | Create an unassigned roster profile with no login account. |
| `match` | Link an explicitly selected `existing_player_id`, without changing that profile. |
| `unchanged` | A previously stored import identity is already linked. |
| `exclude` | Keep this source row out of the roster. |
| `unresolved` | Stop until a reviewer chooses another action. |

Read every name and decision, resolve any `unresolved` entries, then set the top-level `reviewed` value to `true`. Keep the original `raw_name`, `row`, and fingerprint unchanged. UUIDs are durable identities; do not regenerate them to retry an import. The review file is a local operator record, not a cryptographic signature or an app permission grant.

Display names preserve spelling and accents. Whitespace is collapsed and Unicode composed. Only the exact trailing ` Admin ·` badge is removed; the badge-only `Admin ·` row is excluded. Legitimate names containing the word Admin remain unchanged. No case conversion, accent stripping, fuzzy matching, or name-based account takeover is performed.

## Apply and repeat safely

Mount the export folder read-only at runtime:

```sh
realclub run --rm --no-deps --entrypoint python \
  -v "$PWD/tools/messenger-members/out:/imports:ro" backend \
  -m app.import_players --file /imports/members.json \
  --manifest /imports/import-review.json --apply
```

The entire batch runs in one transaction. Errors roll back all player and identity changes. Importers serialize identity lookups on both SQLite and PostgreSQL. Applying the same manifest again returns `unchanged` records, preserving later name, team, skill, availability and other profile edits. Demo-enabled environments and databases containing the demo accounts refuse application.

`player_imports` stores UUID, source namespace, normalized-source-name hash, player ID, original-file fingerprint and creation time. It stores neither the raw chat export nor Messenger permissions. Never delete these mappings to rerun an import. Source-name hashes are identity aids, not anonymization.

An updated export gets a new preview, optionally using `--previous-manifest` to carry earlier decisions and UUIDs. The new report always requires review. Never edit the old fingerprint to force an apply. New or renamed entries after an earlier import are unresolved. For a confirmed rename, choose `match` and copy that person's existing import UUID and player ID from their previous report/mapping. This updates the source mapping while preserving the app display name. For a genuinely new person, choose `create` with a new UUID.

Name collisions never merge automatically. To confirm two distinct people share a name, use distinct UUIDs and `allow_name_collision: true` on their `create` decisions. Duplicate source rows may instead be excluded. Because this export has no stable Facebook IDs, ambiguous renamed or duplicate entries require a human identity decision; row order and name similarity cannot establish identity.

## Administrator and invitations

List imported IDs without creating a login:

```sh
realclub exec db psql -U lex -d lex_pickup -c 'SELECT id, name FROM players ORDER BY id;'
```

After explicitly choosing the real administrator, bootstrap their **existing** profile. Replace the example email and ID with the intended person's values:

```sh
realclub exec backend python -m app.seed \
  --admin-email organizer@example.com --admin-player-id 1
```

The command prompts privately for a password and confirmation. It does not infer the administrator from Messenger roles or names and refuses a profile that already has an account. Omitting `--admin-player-id` creates a separate profile, so include it for imported players.

Sign in at <http://localhost:8081>. In **Club → Members**, invite each existing profile with its owner's email. The single-use link connects the account to the imported record. Captains/admins can open a player's profile and use **Assign primary team**; this does not change historical match-side assignments. Players can fill in their own playing attributes after claiming their profiles. Auto-balance uses a disclosed 5.5/10 estimate for unknown skill and never saves that estimate as a rating.

## Local Python alternative

Configure `DATABASE_URL` for a separate database and `DEMO_ENABLED=false`. For a new SQLite database, from `backend/`:

```sh
export DATABASE_URL=sqlite:///./lex_real.db
export DEMO_ENABLED=false
uv run alembic upgrade head
uv run python -m app.seed
uv run python -m app.import_players \
  --file ../tools/messenger-members/out/members.json \
  --report ../tools/messenger-members/out/import-review-local.json
# Review the new manifest and set reviewed=true before applying.
uv run python -m app.import_players \
  --file ../tools/messenger-members/out/members.json \
  --manifest ../tools/messenger-members/out/import-review-local.json --apply
```

Use the same target database for preview, explicit ID matching, and apply. IDs are local to a database. Preserve both its backups and the matching manifests. The nullable-profile migration preserves existing known attributes; downgrading requires explicitly filling missing values rather than inventing defaults.

## Verification

`uv run pytest -q` exercises malformed sources, review enforcement, Unicode, duplicate/renamed identities, idempotency, rollback, permissions, invitation claims, unknown profiles, balancing and exports. To run the same suite against a disposable PostgreSQL database, set `LEX_TEST_DATABASE_URL` (database name must begin `lex_test_`). These tests own and remove their fixture tables; never point them at club data. Browser coverage verifies profile editing, filters, captain assignments and lineups on desktop and mobile.

## Optional Cosmos provider

The reviewed manifest workflow also works with `DATABASE_PROVIDER=cosmos`; follow [COSMOS_DB.md](COSMOS_DB.md) to initialize the target first. The current 54-player roster fits one atomic batch because provenance is embedded in each player. A larger live import exceeding 100 operations or the safe request-size budget fails before writing; it is never silently split. SQL retains the larger-file behavior. To transfer already imported players, use the offline migration CLI so IDs, profile edits and import UUIDs remain unchanged.
