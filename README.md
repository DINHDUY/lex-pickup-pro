# Lex Pickup Pro

> **This repository was automatically 100% generated by GPT-6-Astra with one [single prompt](./PROMPT.md) using Codex in VS Code.**

**Good football. Great company.** A full-stack clubhouse for a recreational soccer club, built around two fixed teams—**Old Gentlemen** and **Young Boys**—and the shared players who make the games happen.

React 19 · TypeScript · Vite · Tailwind CSS 4 · Radix UI · TanStack Query · React Router · Recharts · FastAPI · Python 3.12 · SQLAlchemy 2 · Alembic · PostgreSQL / SQLite

## What’s included

- A responsive dashboard with the next game, quick RSVPs, recent results, season leaders, and club notices.
- Player profiles with primary team, nickname, shirt number, positions, foot, age group, optional HTTPS photo, availability, injury/absence notes, preferred times, and skill self-rating.
- Dedicated team pages, captain identification, form guides, and fixed-team head-to-head records.
- Game scheduling, editing, calendar/list views, weekly recurring series, location and pitch notes, capacity limits, and phone calendar downloads.
- Going / Maybe / Not going check-ins and a central availability board.
- A pitch-based lineup builder: drag players on desktop, or tap a player then a position on mobile. Skill balancing builds mixed sides from confirmed players.
- Live and post-match scores, goals, assists, own goals, cards, player ratings, and copy-friendly match reports.
- Season and career statistics, leaderboards, goals charts, player comparisons, clean sheets, attendance, reliability, and earned achievements.
- Club notices, roster onboarding, single-use profile invitations, role management, member deactivation, and new seasons.
- Native device sharing, Messenger-friendly summaries, CSV exports, and browser print-to-PDF.
- Light/dark themes, keyboard navigation, accessible dialogs, mobile navigation, installable PWA assets, update prompts, and an offline connection notice.
- A reminder CLI with optional signed webhook delivery, Docker Compose, migration files, explicit demo seeding, backend tests, browser tests, and CI configuration.

The system design and entity relationships are in [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md). Deployment and operation details are in [docs/DEPLOYMENT.md](docs/DEPLOYMENT.md).

After the workflow completes, verify:

- the frontend resolves on the configured hostname

- Keep the Cosmos account and Container Apps in the same region when possible to minimize latency.

## Local development

Requires **Node.js 22.12+** (Node 24/25 also works) and [uv](https://docs.astral.sh/uv/). `uv` manages Python 3.12 and the virtual environment. There is no need to change your system Python.

Start the backend in one terminal:

```bash
cd backend
uv python install 3.12
uv sync --frozen
cp .env.example .env
uv run alembic upgrade head
uv run python -m app.seed --demo
uv run uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

Start the frontend in another:

```bash
cd frontend
npm ci
npm run dev
```

Open **http://localhost:5173**. Vite forwards `/api` to the backend. API documentation is available at **http://127.0.0.1:8000/api/docs**. The database is `backend/lex_pickup.db`, which is excluded from source control. Seeding is idempotent and never resets an existing roster.

If ports are already in use, select free ports and update `FRONTEND_URL` and `CORS_ORIGINS` in `backend/.env`. For example:

```bash
# Backend, from backend/
FRONTEND_URL=http://127.0.0.1:5175 \
CORS_ORIGINS='["http://127.0.0.1:5175","http://localhost:5175"]' \
uv run uvicorn app.main:app --reload --host 127.0.0.1 --port 8001

# Frontend, from frontend/, in a second terminal
API_PROXY_TARGET=http://127.0.0.1:8001 npm run dev -- --port 5175 --strictPort
```

Use **http://127.0.0.1:5175** in this example. Opening the app on another device requires an explicitly allowed origin. Production and PWA installation require HTTPS or localhost.

## Main workflows

### Players

1. Sign in and respond **Going**, **Maybe**, or **Not going** on the overview or match page.
2. Open the match center to see the pitch, time, notes, and lineup. Download the `.ics` file to add it to your calendar.
3. Edit your profile from the account menu. Availability and absence notes are visible to signed-in club members.
4. After a completed game, rate other participants. View your profile for career stats and earned achievements.
5. Use **Share to Messenger** to copy the summary, then paste it into the group chat; **Share…** opens the device’s share sheet when supported.

Games have a hard Going limit. If full, choose Maybe as the reserve list. Captains coordinate replacements; the app does not silently promote reserves. RSVP changes close at kickoff or when the game leaves scheduled status.

### Captains

1. **Schedule game** with a date, time, pitch, format, and squad size. Repeat weekly for up to 12 weeks. Recurrences keep their Eastern local time through daylight saving changes.
2. Open **Lineups**. Choose a player, then a pitch position, or drag them. Save the lineup. Select the other team tab to place that side.
3. **Balance sides** uses Going responses and self-ratings, gives each side a goalkeeper when possible, saves the lineup, and marks the game as mixed. Review positions before kickoff.
4. Use **Match day controls** to start a game. Live goal and own-goal events update the score automatically.
5. Save full time. Both sides must have participants. For post-match entry, save the final score first, then attribute the goals and assists; event totals cannot exceed the saved score.
6. Share the result or lineup. Complete reports are available in the archive.

Saved lineups are locked once the game begins so historical appearances stay stable. A completed score can be corrected, but the game cannot be reopened. Removing a live goal adjusts the score; removing a post-match event changes attribution and leaves the recorded final score intact. To change game size, clear and save the existing lineup first. Editing a recurring game edits that occurrence only.

### Administrators

- Add roster-only players through **Players → Add player**.
- In **Club management**, select **Invite** beside a roster-only player. Enter their email and share the generated link privately. It expires in 7 days and claims the existing profile, preserving history and avoiding duplicate players. Generating a new link invalidates the previous one.
- Alternatively, a new member can register with the club invitation code, creating a new profile.
- Use **Edit** to change primary team, role, or active status. Captains and admins can organize all club games; only admins can manage club access. An admin cannot demote or deactivate their own account.
- Deactivated accounts cannot sign in. Completed-game records remain available.
- Post pitch/equipment notices, export records, or start a new season. New games use the active season; existing matches keep their original season.

## How statistics work

- **Appearances:** a player is in a completed game’s saved lineup.
- **Wins / form:** follow the actual side played, even when the player borrows a shirt or joins mixed sides. Form is ordered by kickoff time.
- **Goals / assists:** attributed goal events in completed games. Own goals affect the score but do not count toward the scorer’s Golden Boot total.
- **Clean sheets:** every participating player receives one when their side concedes no goals. This is a team clean-sheet participation metric, not a goalkeeper-only statistic.
- **Rating:** average of submitted participant/organizer ratings; one editable rating per author/player/game. Self-ratings after a game are blocked.
- **Attendance:** appearances divided by completed club games in the selected period.
- **Reliability:** appearances following a Going response divided by all Going responses for completed games; blank if there are no such responses.
- **Head-to-head:** classic Old Gentlemen vs Young Boys games only. Mixed games still count toward individual and overall club statistics.
- **Achievements:** derived from recorded performance. Profile achievements include double-digit goals, club regular, Iron Man, and an 8+ average rating. Golden Boot and Playmaker leaders are displayed in statistics.

The overview uses the active season; profiles show career statistics. The analytics screen can select a season or all-time records. CSV player exports are career totals and are labelled accordingly. Print a selected analytics view to save that season as PDF.

## Messenger and reminders

The app complements your existing group. It does **not** impersonate a Facebook account or automatically post to personal Messenger group chats. On supported phones, Messenger may be chosen from native sharing; otherwise paste the copied summary into Messenger. Links require club sign-in and return members to the requested match.

Preview reminders for games in the next 24 hours:

```bash
cd backend
uv run python -m app.reminders
```

For automatic delivery to an integration you own, set `REMINDER_WEBHOOK_URL` to an HTTPS endpoint and `REMINDER_WEBHOOK_SECRET`, then schedule `python -m app.reminders --deliver` hourly. Payloads use `X-Lex-Signature` (HMAC-SHA256 of the raw body) and an `Idempotency-Key`. Successful deliveries are deduplicated; the receiver must also honor idempotency to handle retries after a partial job failure. Integration details are in [docs/DEPLOYMENT.md](docs/DEPLOYMENT.md).

## Scope and operational notes

This application contains working local and deployment source; production readiness also depends on your hosting configuration and operational checks. Configure PostgreSQL or the optional Cosmos provider, HTTPS, backups, and the supplied acceptance checks before opening a real club. Configuration rejects the default signing secret, insecure cookies, demo mode, and default invitation code in production.

Photos use HTTPS URLs rather than file uploads. PDF export uses the browser’s print dialog. There is no payment collection, financial ledger, automatic email service, social login, or Messenger bot. Password recovery is administrator-assisted through the documented CLI. Static PWA assets are cached; authenticated API data is not cached by the service worker, and offline edits are not queued. A shared rate limiter is required before running multiple API workers.
